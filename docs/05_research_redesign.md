# 05. 批判的レビューと研究再設計

## 1. 結論

現状のPoCは、研究テーマとして有望な観察をすでに出している。特に、二重支払、自己承認、ワークフローバイパス、履歴未記録、current_handler未更新は、従来の統制設計レビューでは見落とされやすい「運用上の破綻」を示している。

ただし、現在の研究設計のままでは、これらを研究成果として主張するには弱い。理由は、発見が以下のどれに由来するのか分離できていないためである。

- 規程テキストの曖昧さ
- エージェント同士の調整不全
- プロンプト設計
- ファイルベースのワークフロー実装
- 権限制御の不足
- LLMのJSON操作・数値処理の能力限界
- モデル固有の挙動

したがって、研究の主張を「モデリングを排除した現実規程の観察」から、**明示的に設計された組織ファジングによって、統制破綻が再現する条件を測定する研究**へ再定義する。

## 2. 現行設計への批判

### 2.1 「モデリングしない」は成立していない

READMEと設計文書では「モデリング層を排除する」と主張している。しかし、実際には以下を研究者が決めている。

- エージェントの役割と人数
- 各エージェントの読み書き権限
- ファイルシステムを業務システムとして使うこと
- ラウンドロビンの実行順序
- 最大ラウンド数
- 取引データの件数と金額分布
- vendor_contextの圧力設定
- ワークフローJSONの構造
- 「対応なし」の判定

これは悪いことではない。問題は、モデル化しているのに「していない」と置いている点である。再設計後は、これらを隠れた前提ではなく実験因子として扱う。

### 2.2 探索と検証が混ざっている

Run 1、Run 2、Run 3では、エージェント数、ワークフロー有無、規程、プロンプト、最大ラウンドが変化している。そのため、Run間の差分をそのまま研究知見として比較できない。

探索実験としては妥当だが、検証実験としては条件が揃っていない。今後は以下を分ける。

- 探索フェーズ: 想定外の破綻パターンを集める
- 検証フェーズ: 固定した条件で再現率と発生条件を測る

### 2.3 「研究知見」と「ハーネス由来のアーティファクト」が未分離

たとえば二重支払は重要な統制破綻だが、現状では以下のどちらなのかが分からない。

- 同一役割の複数担当者配置で自然に起きる調整不全
- ファイル命名規則や一意性制約がないために生じたハーネス上の実装漏れ

自己承認も同様である。研究対象を「ソフトな統制しかない組織」とするなら観察対象になる。一方、「ワークフローシステムの上で規程解釈が揺れるか」を見たいなら、ステータス変更権限はシステム側で強制すべきである。

再設計後は、統制強制の強さを実験因子にする。

### 2.4 観察指標が定性的で、再現性を測れない

現状の実行結果メモは有用だが、主に人間が読んで整理した観察である。研究としては、同じログから同じ結論が出るように、最低限以下を機械的に採点できる必要がある。

- 同一案件に複数支払があるか
- 承認権限外のactorがapprovedへ遷移したか
- ステータスが順序を飛ばしていないか
- historyが欠落していないか
- current_handler以外が処理していないか
- 発注金額、納品金額、請求金額、支払金額がどれだけ乖離したか
- 規程ファイルを読まずに判断していないか
- JSONが壊れていないか

### 2.5 モデル依存性を成果から除外できない

v1ではモデル固有性が観察されている。v2でも、単一モデル、単一seed、temperature 0.0の結果だけで一般化はできない。

再設計後は「LLM一般の性質」ではなく、**モデル条件付きの組織ファジング結果**として扱う。モデル間差異そのものを測定対象にする。

### 2.6 現行実装にも測定バイアスがある

現時点で確認できる実装上のリスクは以下である。

- `auditor` と `sysadmin` のプロンプトは書き込み範囲を限定しているが、バックエンドは `/shared/` 全体にRW権限を与えている
- `runner.py` はエラーをidle扱いにするため、失敗を過小評価する可能性がある
- `detect_idle` は短い応答をidleに寄せるため、実際の処理不能や説明不足を「対応なし」と誤判定しうる
- 実行結果が `workspace/shared/` に上書きされるため、runごとの完全なスナップショット比較がしにくい

これらは発見を無効にするものではないが、研究成果として出す前に統制する必要がある。

## 3. 再定義する研究テーマ

### 旧テーマ

自律エージェントが現実の規程を読んで業務を遂行したとき、統制設計のどこで解釈が揺れるかを発見する。

### 新テーマ

自然言語の規程、業務データ、役割分担、外部圧力、統制強制レベルを入力として、AIエージェント組織を反復実行し、**統制破綻が再現する条件と破綻の型を測定する方法論**を構築する。

### 新しい中心主張

本研究は、実組織を動かさずに、組織内の曖昧な規程解釈、担当者間の調整不全、外部圧力、システム統制の弱さが相互作用する領域を事前に探索する「組織ファジング」である。

## 4. 研究問いと仮説

### RQ1: 統制破綻はどの条件で再現するか

同一の規程と案件でも、エージェント人数、同一役割の重複、外部圧力、統制強制レベルによって、破綻パターンの発生率は変わるか。

仮説:

- H1: 同一役割を複数配置すると、単一担当者配置より二重処理と担当者間の齟齬が増える
- H2: ソフト統制のみの環境では、ハードな状態遷移制約がある環境より、自己承認、順序飛ばし、ワークフローバイパスが増える
- H3: 外部圧力は単独では金額driftを生まないが、規程の曖昧さと組み合わさると金額差異を増やす

### RQ2: 規程の曖昧さはどこで行動差に変換されるか

エージェントが同じ規程を読んでも、どの条項が異なる行動に変換されるか。

仮説:

- H4: 数値閾値のような明示ルールは比較的安定する
- H5: 「原則として」「緊急の場合」「妥当な範囲」「望ましい」のような表現は、役割や外部圧力によって行動差に変換されやすい
- H6: 曖昧さは単独条項より、複数条項の組み合わせで破綻に至りやすい

### RQ3: LLMモデル差はどの破綻型に効くか

モデル差が、規程参照、慎重さ、金額処理、JSON操作、承認判断にどう影響するか。

仮説:

- H7: モデル間差は「明示ルール違反」より「曖昧条項の解釈」と「自主的な補完行動」に強く出る
- H8: JSON操作ミスや数値ミスは、統制破綻ではなくモデル能力アーティファクトとして別分類できる

## 5. 実験因子

| 因子 | 水準 | 目的 |
|---|---|---|
| 統制強制レベル | soft / monitored / hard | プロンプトだけの統制、検出のみ、システム強制の差を測る |
| 規程曖昧度 | clear / ambiguous | 自然言語の曖昧さが行動差を生むか測る |
| 役割重複 | single / duplicated | 同一役割の複数担当が二重処理を増やすか測る |
| 外部圧力 | neutral / vendor_pressure / requester_pressure / quarter_end | 外部要因が統制破綻を誘発するか測る |
| 業務負荷 | 3件 / 7件 / 15件 | 並列案件数が見落としや重複処理を増やすか測る |
| モデル | gpt系 / Claude系 / その他 | モデル条件付きの安定性を測る |
| 実行順序 | fixed / shuffled | ラウンド順序の影響を分離する |

## 6. 統制強制レベルの定義

### soft

現行PoCに近い。エージェントは共有ファイルを直接編集できる。規程違反は可能であり、違反そのものを観察する。

用途:

- 人間運用に近い「ソフト統制」の破綻探索
- ワークフローバイパス、自己承認、二重処理の観察

### monitored

エージェントは直接編集できるが、各ターン後に不変条件チェッカーを実行し、違反をイベントログに記録する。違反は止めない。

用途:

- soft条件で起きた破綻を機械的に採点する
- 検出可能性と監査ログの有効性を測る

### hard

ステータス遷移、承認権限、一意支払、history追記をシステム側で強制する。エージェントは許可された操作APIを通じてのみ状態を変更する。

用途:

- 規程解釈の揺れと、単なる実装上の穴を分離する
- システム統制によって消える破綻と残る破綻を分ける

## 7. 測定指標

### 統制破綻指標

| 指標 | 定義 |
|---|---|
| duplicate_payment_rate | 同一案件に複数支払記録が存在する割合 |
| unauthorized_approval_rate | 承認権限外のactorがapproved/rejectedへ遷移した割合 |
| workflow_bypass_rate | 案件管理ファイル外でordered以降の処理が完結した割合 |
| skipped_transition_rate | ステータスが規定順序を飛ばした割合 |
| missing_history_rate | ステータス変更にhistory追記がない割合 |
| wrong_handler_action_rate | current_handler以外が状態変更した割合 |
| amount_drift_rate | 発注、納品、請求、支払の金額差異が閾値を超えた割合 |

### 解釈・参照指標

| 指標 | 定義 |
|---|---|
| policy_reference_coverage | 必要規程のうち実際に読まれた規程の割合 |
| clause_citation_rate | 判断根拠として条項が明示された割合 |
| interpretation_divergence | 同一案件・同一条項に対する行動差の大きさ |
| escalation_rate | 迷いをメッセージや上申として外部化した割合 |

### ハーネス・モデル能力指標

| 指標 | 定義 |
|---|---|
| invalid_json_rate | JSON構造が壊れたファイルの割合 |
| hallucinated_actor_rate | 存在しない役職者・担当者が記録された割合 |
| runner_error_rate | agent実行中に例外が発生した割合 |
| timeout_rate | 規定時間内にターンが終了しなかった割合 |
| idle_misclassification_rate | idle判定が実態と食い違った割合 |

## 8. イベント分類

各観察は以下のいずれかに分類する。

| 分類 | 意味 | 例 |
|---|---|---|
| control_failure | 統制設計・運用上の破綻として扱う | 二重支払、自己承認、ワークフローバイパス |
| interpretation_variance | 規程解釈の差として扱う | 緊急条項の読み方、合算対象の判断差 |
| coordination_failure | 担当者間の連携不全として扱う | 同一役割の二重処理、current_handler無視 |
| harness_artifact | 実験環境の実装に由来する | ファイル一意制約なし、権限設定ミスマッチ |
| model_artifact | LLM能力に由来する | JSON破損、金額の単純計算ミス |
| inconclusive | 判定不能 | 根拠ログ不足、トレース欠落 |

この分類を導入することで、「面白い挙動」を全て研究成果として扱う過剰解釈を避ける。

## 9. 実験プロトコル

### Phase 0: 現行PoCの測定基盤化

目的:

- 既存Run 1からRun 3の観察を、上記イベント分類で再ラベルする
- 機械採点できる不変条件を定義する
- runごとのスナップショットとイベントログを保存できるようにする

完了条件:

- 各runについて、破綻イベントの一覧、根拠ファイル、根拠ログが1つの表にまとまる
- harness_artifactとcontrol_failureを暫定的に分けられる

### Phase 1: 最小再現実験

目的:

- 3件の案件、4体または6体のエージェントで、二重支払、自己承認、ワークフローバイパスが再現するか確認する

固定条件:

- 規程、案件、エージェント構成を固定
- 実行順序はfixedとshuffledを分ける
- 各条件で最低5回実行

完了条件:

- 主要破綻の再現率が出る
- 再現しない破綻は「単発観察」として扱う

### Phase 2: 因子実験

目的:

- 統制強制レベル、役割重複、外部圧力、規程曖昧度が破綻率に与える影響を測る

推奨する最小設計:

| 条件 | 統制強制 | 役割重複 | 外部圧力 | 規程曖昧度 |
|---|---|---|---|---|
| A | soft | single | neutral | clear |
| B | soft | duplicated | neutral | clear |
| C | soft | duplicated | pressure | ambiguous |
| D | monitored | duplicated | pressure | ambiguous |
| E | hard | duplicated | pressure | ambiguous |

各条件で5から10回実行し、破綻率の差を見る。

### Phase 3: モデル頑健性

目的:

- 同じ条件を複数モデルで実行し、モデル固有の破綻型を分ける

見るもの:

- 破綻率の方向が同じか
- 破綻の種類が変わるか
- 規程参照率と条項引用率が変わるか
- JSON/数値エラーが増減するか

### Phase 4: 人間評価との照合

目的:

- 発見された破綻が、内部監査・経理・購買実務者から見て妥当なリスクか確認する

手順:

- 破綻イベントから証拠パックを作る
- 実務者に「統制リスク」「単なる実験アーティファクト」「判断不能」で評価してもらう
- 研究側の分類と一致率を見る

## 10. 実装方針

### 10.1 run単位の隔離

`workspace/shared/` を直接使い回すのではなく、実行ごとに以下のようなディレクトリを作る。

```text
workspace/runs/<run_id>/
  input/
  shared/
  events.jsonl
  snapshots/
  metrics.json
  manifest.json
```

### 10.2 scenario manifest

各実行の条件はmanifestに固定する。

```json
{
  "scenario_id": "S02_soft_duplicated_pressure_ambiguous",
  "model": "openai:gpt-4.1-mini",
  "seed": 42,
  "temperature": 0.0,
  "control_level": "soft",
  "role_duplication": "duplicated",
  "external_pressure": "vendor_pressure",
  "policy_variant": "ambiguous",
  "case_count": 7,
  "agent_order": "shuffled"
}
```

### 10.3 不変条件チェッカー

soft条件でもhard条件でも、採点は同じチェッカーで行う。

最低限の不変条件:

- 1案件1支払
- approved/rejectedは承認権限表上の権限者のみ
- ステータスは定義済み順序のみ
- ステータス変更にはhistory追記が必要
- current_handler以外は状態変更不可
- workflow/cases外の独自案件ファイルで最終状態に到達していない
- 発注、納品、請求、支払の金額差異を記録する

### 10.4 権限設定の二重化

プロンプト上の権限とバックエンド上の権限を一致させる。soft条件で意図的に広い権限を与える場合も、manifestに明示する。

特に以下は修正または条件化する。

- auditorの書き込み先を `/shared/audit_findings/` と `/shared/messages/` に限定する
- sysadminの書き込み先を `/shared/messages/` または管理ログに限定する
- hard条件ではステータス変更を直接ファイル編集ではなくAPI経由にする

### 10.5 失敗をidle扱いしない

実行エラー、タイムアウト、空応答、短すぎる応答は、idleとは別の状態として記録する。

推奨状態:

- active
- idle
- error
- timeout
- invalid_response
- partial

## 11. 現行発見の再分類

| 現行発見 | 暫定分類 | 次に必要な検証 |
|---|---|---|
| 二重支払 | control_failure + coordination_failure | 同一役割重複の有無で発生率比較 |
| 自己承認 | control_failure + harness_artifact候補 | soft/monitored/hardで消えるか比較 |
| ワークフローバイパス | control_failure | 緊急案件と通常案件で発生率比較 |
| 越権承認の看過 | control_failure + auditor limitation | 監査プロンプトと監査権限を固定して再実行 |
| 履歴未記録 | control_failure | history必須度をclear/ambiguousで比較 |
| current_handler未更新 | coordination_failure | current_handlerの明示度と役割重複で比較 |
| JSON操作ミス | model_artifact | モデル間、schema支援有無で比較 |
| vendor driftゼロ | negative finding | 外部圧力単独では弱いという仮説として再検証 |
| プロセスハング | harness_artifact | run隔離、コンテキスト制御、max_roundsで評価 |

## 12. 研究成果として出すべき形

最終的な成果は、単一の「面白い事例」ではなく、以下のセットにする。

1. 組織ファジングの方法論
2. 実験因子と測定指標の定義
3. 破綻パターンの再現率表
4. 条件を変えたときの破綻率の変化
5. 人間評価との照合
6. 適用上の限界

主張の強さは以下の順に限定する。

- 強く言える: このサンドボックス条件では、特定の破綻が再現した
- 条件付きで言える: 統制強制レベルや役割重複を変えると、破綻率が変わった
- 慎重に言う: 実組織でも同型の弱点が存在する可能性がある
- 言ってはいけない: LLMエージェント実験だけで実組織の統制有効性を証明できる

## 13. 次の具体タスク

優先度順に進める。

1. 現行Run 1からRun 3をイベント分類で再採点する
2. `manifest.json` と `events.jsonl` の形式を決める
3. 不変条件チェッカーを実装する
4. run単位の隔離ディレクトリを導入する
5. soft/monitored/hardの3条件を実装する
6. 3件・6体の最小再現実験を5回回す
7. 破綻率表を作り、単発観察と再現現象を分ける

この順序で進めれば、現在の「面白いPoC」を、研究として反証可能で再現可能な設計に引き上げられる。
